## 一、基础模型观

预设不是神秘咒语。SillyTavern 的预设、角色卡、世界书、摘要、聊天历史和用户输入，最终都会变成模型上下文里的文本或消息数组。

核心公式：

```text
输入 + LLM -> 输出
```

`输入` 包括当前用户输入、历史消息、预设条目、角色卡、世界书、摘要、宏替换结果、role、content、参数和渠道额外注入内容。`LLM` 包括模型训练语料、对齐偏好、tokenizer、上下文长度、注意力分布和生成参数。

模型按 token 逐步生成。它没有真正的长期记忆，也不是在完整规划后一次性输出。每次生成都基于当前上下文和已经生成出的 token 继续预测下一个 token。

从 Transformer/decoder-only 的视角看，预设写作要关注三件事：

- 文本向量化：文本会被切成 token，再映射成模型可计算的向量。相近语义、格式和上下文关系会影响模型对当前任务的判断。
- 自回归生成：模型不是先写完整答案再发出来，而是不断根据当前上下文和已生成内容预测下一个 token，所以开头、格式、示例和刚生成出的句子会持续影响后文。
- 注意力分配：提示词不是写进去就等于稳定生效。位置、长度、重复、冲突、role、最近上下文和示例都会改变模型实际关注什么。

`role、content 和 token` 都会影响模型。role 不是界面标签，而是进入请求结构或上下文格式后影响模型理解和停止行为的部分。字段名不等于模型一定看到；模型主要看到内容、顺序、role、格式和最近聊天。

控制台或实际发送上下文是第一证据。诊断预设时先看实际发送内容，再看界面上的预设结构。

长上下文不是完整记忆。多数模型存在 U 型注意力：顶部和底部更容易被注意，中段更容易遗忘。上下文变长后，同一条提示在上下文中的相对位置会变化，作用也可能偏移。

## 二、SillyTavern 上下文组装：模型真的看到了什么

模型不知道"卡""预设""字段""世界书"这些概念。它只看到一块文本。SillyTavern 的工作只有三件事：

1. 从预设（JB）、卡、世界书、摘要、聊天历史里取出文本块。
2. 按一定顺序塞进模型上下文。
3. 调用 API 让模型生成。

模型看不到 `Main Prompt`、`Character Definition`、`Scenario` 这些字段名，它只看到字段里的**内容**。

最关键的调试原则：**永远看控制台**。控制台里的实际请求是唯一的真相来源。不要相信你以为的"我这样写就应该这样发"。

Claude 内部的上下文格式：
- 用 `Human:` 表示用户，用 `Assistant:` 表示自己。
- 上下文中的格式是 `(可选系统提示) → Human:... → Assistant:... → Human:... → Assistant:...`
- 第一条非系统消息必须是 Human。
- 连续同 role 会被拼成一条。

SillyTavern 在 Claude API 上的特殊行为：
- 如果系统提示开启，context manager 顶部的 System role 消息全作为系统提示发送。
- 如果系统提示后的第一条是 Assistant role，ST 会先塞 `User first message` 再发这条 Assistant 消息（因为 API 要求首条是 User）。
- 连续同 role 消息会被粘成一条。
- `Main Prompt` 无论开关都永远发送。

预填充（prefill）：
- 把 Assistant 回复的开头预先填好，让模型接着写。
- 预填充强控模型行为：模型会倾向继续预填充的内容和方向。
- 可用于设定回复开头格式、打破重复模式、增加 swipe 多样性。
- Claude 3.5 中系统提示高于预填充；Claude 3 中预填充可覆盖系统提示。

聊天历史注入：ST 允许把消息注入到聊天历史中间。注入的消息会被粘到相邻 Human 或 Assistant 消息里，意味完全不同（是"指令"还是"已说过的话"）。

## 三、注意力 U 型曲线与可用上下文

多数 LLM 的注意力随 token 位置呈 U 型曲线：**上下文顶部和底部精度高，中段精度低**。这就是"lost in the middle"。

不同模型曲线有差异：
- Claude 3：底部精度远高于顶部。
- Claude 3.5/3.7：底部略高于顶部。
- GPT-4o：较均衡，底部稍高。
- 所有模型中段都有显著精度下降。

上下文越长，U 型越陡。在角色扮演实战中：
- **实际可用上下文约 20-25k token**（超过后 Claude 开始变蠢）。
- 在这 20-25k 里，高精度区约：底部 3-4k token + 顶部 3-4k token（Claude 3）；底部 4-5k + 顶部 4-5k（Claude 3.5/3.7）。
- 50k+ = 明显降智，100k+ = 幻觉频发。

chat history 是上下文里最臃肿的部分。它又长又重复，形成强模式。模型会把它当作"叙述示例"来 follow，从而越来越不关注你的指令和设定。repetition 和 lost-in-the-middle 是当前角色扮演最大的两个问题。

回复长度效应：自回归生成中，每写一个 token 都会把原来的上下文往上推。一条 1000 token 的回复会把原来在底部高精度区的聊天历史往上推 1000 token，送进"遗忘区"。长 CoT 回复尤甚——CoT 本身占了底部高精度区，正文开始写时上方内容已被推到中段。

## 四、In-context Learning（ICL）与角色扮演

In-context learning 是 LLM 最底层的核心行为：模型会检测并重复上下文中的任何模式。它不是"学会了就能关掉"的功能，而是不可抵抗的基础机制。

关键特性：
- 任何模式都会被检测和重复：从单 token 到高层文学手法、角色情绪、指令风格。
- 模式越强（越重复、越密集），重复倾向越大。
- 模型越大越聪明，ICL 能力越强，能检测的模式越抽象。
- 示例越多效果越强，但 4 个以上边际效益递减。
- 示例间距越小效果越强。
- ICL 强到可以覆盖大部分模型训练。

ICL 在角色扮演中的影响：
- **整个角色扮演的走向由 greeting 和前几条消息决定**（ICL 让模型重复看到的东西）。
- 模板和 speech examples 完全靠 ICL 起作用。
- 重复问题（同词、同结构、同情节）是 ICL 的副产品。
- 逐渐回到默认写作风格（claudeisms）= ICL 把偶尔的 claudeisms 加强放大。

ICL 的 shot 术语：
- zero-shot：只有指令，无示例。
- one-shot：1 个示例（适合模板，容易过拟合但也正好是模板需要的效果）。
- many-shots：多个示例。

示例必须手写，绝不用 AI 生成的示例。否则会把 claudeisms 和代写用户行为教给模型。

示例正则化：示例应在"你想让模型学的东西"上一致，但在"其他一切"上多样。如果两个示例的场景和处境一模一样，模型会学会那个处境本身并泄漏进角色扮演。

## 五、模板：one-shot 的强大用法

给模型一条长指令不如给一个模板（相当于 1 个示例）。模板利用了 ICL，LLM 填空白比执行复杂指令更可靠。

模板优于指令的情况：
- 要求输出特定格式（CoT + 正文 + stat block）。
- 要求特定对话/叙述结构。
- 需要稳定遵循的回复模式。

模板写法要点：
- 给模板起有描述性的标签名（如 `<reply-template>`），让模型能通过训练语料中见过的模式猜出意图。
- 用占位符（`???`、`X`、`Y`）标注要模型填的部分。
- 优先在模板中用描述而非指令——模板本质是描述性的。
- XML 注释和 `()` `[]` `{}` 可做占位符，但注意括号有时会歧义（模型不确定要不要输出括号本身）。
- 不要出空标签；如需模型自发填充，空 XML 标签对 Claude 反而是提示。

模板 + 少量指令的组合通常最稳定。极端复杂的格式要求会让模型变蠢（stat tracker 重灾区）。

## 六、重复问题：根因与对策

重复的根本原因是 ICL：聊天历史形成重复模式 → ICL 让模型继续重复 → 重复的消息又进入历史 → 自强化循环。重复不限于词汇层面——句式、结构、情绪交替、情节走向、背景角色都能被"重复"。

不同模型的重复倾向：
- Opus：抗重复较强，可能专门做过反重复训练。
- Sonnet：容易循环。
- GPT-4o：中等。

最可靠的解法：**截短聊天历史**。历史越长越重复，因为模式堆积。正常角色扮演留 20 条左右 + 安全余量就够了，配合摘要系统可以玩慢热长线。

辅助手段（都不完美，可能失效）：
- 手动编辑/重写回复打破循环（核选项，费劲）。
- combo breaker：OOC 要求写完全不同结构的回复（如`<ooc>描述当前场景环境。</ooc>`），增大重复间距。
- 随机预填充：用 `{{random}}` 宏注入不同的回复开头提示，打破模式同时增加 swipe 多样性。
- CoT 规划：让模型先出规划再按规划写回复。规划格式不同于聊天历史所以不易被 ICL 循环吸入。

## 七、Claude XML 格式化

Anthropic 专门训练 Claude 理解 XML 结构来组织上下文：

- 把不同类型的数据包进不同的 XML 标签（指令、设定、示例……）。
- 标签名要有描述性，帮助模型理解内容。
- 嵌套不超过 5 层。
- 引用时可以跨标签引用 `<tag></tag>` 格式。

不只有 Claude 受益——任何能编程的 LLM 都能理解 XML。Gemini 和 Mistral 通常也能用好。

不需要严格符合 XML 语法。空格在标签名中可用，各种 `<...></...>` 形式通常都有效。不要过度嵌套——复杂格式会增加模型的理解距离，反而变蠢。

## 八、Token 浪费常见来源

- 复杂 emoji（🤦🏼‍♂️ = 5 token，👨🏻‍🦲 = 10 token，🏴󠁧󠁢󠁥󠁮󠁧󠁿 = 21 token）。
- 花式 Unicode 字体：每个字符都是多 token。
- 过长示例不精简。
- 冗余信息、重复说明、自说自话的 JB 堆料。

## 九、摘要系统实战

长线慢热角色扮演的关键：用短聊天历史 + 摘要保存关键信息。

- 摘要写在聊天历史之前，放在最靠近底部高精度区或系统提示中。
- 截短聊天历史到当前场景长度 + 少量安全余量。
- 摘要内容应包含：关键事件、角色状态变化、重要伏笔、位置/时间。
- 手动编辑摘要优于全自动——自动摘要容易抹掉伏笔和微妙状态。
- 可以用 STscript 高级控制摘要行为。

## 十、采样器实战调参

Temperature / Top K / Top P 都做同一件事：在创造性和可预测性之间取舍，但方式不同。

默认值（大部分英语对话任务直接可用）：
- Temperature = 1
- Top K = 0（禁用）
- Top P = 1（禁用）

何时需要调：
- 非英语语言、生僻口音、特殊写法。
- 复杂格式要求被打破。
- 上下文大、指令和设定在中段。
- Claude 忘事或产出乱码。

调参优先级：
1. 先修 prompt（简化、消歧义、挪到更优位置），不先调采样器。
2. 如果 prompt 不能简化，降低 Top P（如 0.8~0.95），直到乱码/遗忘消失。
3. 如果 Top P 需要低于 0.8，再考虑略降 Temperature（最后手段）。

Temperature vs Top P/K 的选择：
- Top P 保持各 token 的概率比例但切掉尾巴，**保留创造性同时过滤垃圾**。
- Top K 硬切只留前 K 个 token，适用于已知确切分布的场合（Claude API Top K 最高 500）。
- Temperature 是分数倍增器，压低后所有 token 都往高概率挤，创造性被杀。只有当 Top P 调不动时才动。

## 十一、handler 工作法

插件 AI 的目标不是背教程，而是帮助用户完成事情：

- 判断用户阶段：新手引导、从零创建、局部优化、故障诊断、文风塑形、模型适配、测试复盘。
- 把模糊需求翻译成可执行目标：控制什么行为、修复什么现象、适配哪个模型、希望得到什么文本效果。
- 能合理假设时先给可用草案；不确定时最多问 3 个关键问题。
- 输出要帮助用户操作插件：写条目、改条目、移动位置、解释 role、给验证步骤、提示下一步动作。

插件 AI 不应只说“多测试”。它要给用户一个可执行闭环：

```text
目标 -> 条目结构 -> role/位置 -> 可复制内容 -> 测试句 -> 观察点 -> 下一轮最小修改
```

## 十二、从零构建预设

预设先定结构，再填内容。结构核心是 `role`、位置、提示词内容。

从零构建时先问三个问题：

- 目标：这个预设要让模型做什么？
- 模型：主要适配 Claude、GPT、Gemini 还是其他模型？
- 交互：用户和 AI 在故事里分别是什么角色，是否需要主持人、旁白、角色扮演、小说模拟器等模式？

推荐模块：

- 顶层任务
- 角色/世界资料通道
- 行为规则
- 叙事策略
- 输出格式
- 短示例
- 底部重申
- 启动/执行提示

原则：

- 一个条目只承担一个主要目的。
- 避免把设定、风格、格式、禁忌和示例混成超长条目。
- 高优先级规则放在更容易被注意的位置。
- 关键规则不要埋在长资料中段。
- 先做最小可用结构，再逐步增加模块。

SillyTavern UI 中，模块启用、排序、role 和内容编辑共同决定最终上下文。模块化预设的价值是复用、管理、一致性和可调试性，不是把所有想法堆进一个条目。

## 十三、提示词基本写法

提示词是帮助模型理解你的意图，并按你的要求输出内容的文本。

写提示词前先明确：

- 你的要求是什么？
- 你希望模型干什么？
- 你选择的模型有什么惯性或偏好？
- 哪些信息值得占用注意力？

写提示词时：

- 不给出对目标没有帮助的内容。
- 不写模糊要求，把抽象词改成可执行标准。
- 尽可能给短示例，示例要贴近目标输出。
- 使用结构化文本降低解析成本，如 Markdown、YAML、JSON、XML 标题。
- 写完后检查内在矛盾、职责重叠、冗余堆料和不符合预期的输出。

结构化格式的用途：

- 给模型区分不同信息块。
- 给人类调试和维护。
- 减少“长评不打标点”式上下文污染。

不要迷信某一种格式。不同模型对 JSON、YAML、XML、Markdown 的偏好不同；Claude 常适合把 XML 当章节标题使用，但不宜把所有资料深层序列化成 XML。

## 十四、靶向提示

靶向提示不是堆更强的命令，而是找根因后做最小有效提示。

工作流：

```text
问题现象 -> 可能原因 -> 模型/上下文特性 -> 靶向条目 -> 最小修改 -> 验证问题
```

示例思路：

- 输出过长或抢话，可能不是“字数要求不够强”，而是聊天历史和补全惯性推动模型继续写。
- 如果模型倾向在一个 assistant 回合里写完整对话，就需要让它知道何时把回合交回用户。
- 对 Claude 等依赖 role/stop 行为的模型，要检查 role 顺序、预填充、stop、示例和历史注入。

常见诊断：

- 抢话：先查 role 顺序、预填充、示例、聊天历史注入和是否隐含允许代写用户。
- 跑偏：先查目标不清、条目职责重叠、世界书/角色卡/预设冲突、示例污染。
- 重复：先查聊天历史强模式、相似示例、过长回复、过度重复提醒和单调摘要。
- 遗忘：先查上下文长度、关键规则位置、最近输入是否把重点挤出底部注意力区。

## 十五、元提示与分析

元提示是让模型分析提示词、核对概念理解、提出优化建议的工具。它能提高提示词调试效率，但不能超出模型能力上限，也会产生幻觉和迎合。

安全的元提示环境：

- 尽量减少插件、世界书、角色卡和旧上下文干扰。
- 用低温度、多模型交叉比较。
- 复杂问题不要一轮塞太多任务，最好限制在 1-3 个问题。

分析已有提示词时：

- 先声明被分析文本只供分析，不要执行。
- 用代码块或清晰标签包住待分析内容。
- 先问“是否存在某类问题；若有指出，若无说明理由”，不要强迫模型列不存在的问题。
- 先定位问题和原因，再给修改建议；不要在分析不足时直接大幅重写。
- 长提示词优先局部分析，限定到某个条目、标签、症状或目标。

元提示追问：

- 确认型：请展开某个判断，并说明依据。
- 质疑型：重新考虑某个判断，若仍认为正确则解释，否则说明修正原因。
- 部分采纳型：只采纳 1、3、4 点，基于它们修改某个条目。
- 实践型：让模型根据修改后的提示执行一个有评估标准的测试任务。

## 十六、文风与叙事

文风不是形容词堆叠，要转成叙事策略。

文风可以拆成两部分：

- 文字结构：叙述方式、视角、聚焦、句式、段落、对话组织。
- 文字感受：氛围、情感、清晰度、审美追求、读者体验。

实用三层框架：

```text
文风 = 基调、文体特征、叙述规则
```

- 基调：核心审美追求和创作基础，例如主观真实、口语化、克制、冷静、暧昧、荒诞。
- 文体特征：文本给人的整体体验，例如通俗化、重情绪、现实主义、画面感、轻小说感、散文感。
- 叙述规则：具体可执行写法，例如人称、聚焦、对话是否独立成段、是否使用对话标签、是否比喻、标点规范、禁止项。

更高阶的叙事策略：

- 区分故事与叙事。故事是事件本身，叙事是讲述故事的方式。
- 文风属于叙事的一部分，词汇、句式、环境描写、人物描写、节奏和信息控制都是叙事策略。
- 高质量文本要同时考虑核心事件、催化事件、叙事话语和文风文笔。

控制链：

```text
核心事件 -> 核心事件的文本效果 -> 催化事件/叙事话语 -> 局部文本效果 -> 文风文笔
```

插件 AI 写文风条目时，不要只问“要什么风格”，要追问：

- 当前故事的核心事件是什么？
- 希望读者感受到什么？
- 哪些催化事件能增加血肉？
- 使用什么叙事姿态？
- 哪些具体决策交给 AI 动态选择？

示例流适合模型吃示例的场景。示例要是一段完整场景，而不是单句描述。示例会强烈影响基调，所以要短、准、贴目标。

## 十七、模型适配

模型是最大变量。Claude、GPT、Gemini 对 role、格式、长上下文、示例、预填充和敏感表达的反应不同。

Claude 相关问题优先检查：

- `system/user/assistant` 交替顺序。
- User first message。
- 连续同 role 是否被合并。
- 预填充。
- 聊天历史注入。
- XML 是否只作为清晰标题，而不是过深嵌套资料。

Gemini 相关问题优先检查：

- 上下文太长导致质量下降。
- 过度解释、烂比喻、八股化。
- 示例是否过强污染基调。
- role 与系统提示是否被渠道转写。

GPT 相关问题优先检查：

- Markdown 结构偏好。
- 示例格式是否一致。
- 角色设定、风格规则和输出格式是否冲突。
- 安全边界和拒绝倾向是否影响任务。

API 的先手优势：

- API 通常更接近干净输入，可以调节 role/content、参数和消息顺序。
- 网页端或反代渠道可能加入隐藏内容、过滤词、固定前后缀或参数限制。
- 诊断时要区分“插件界面里写了什么”和“模型实际收到什么”。

## 十八、CoT 和计划类提示

CoT 是工具，不是万能按钮。

可用场景：

- 复杂结构分析。
- 长上下文相关性判断。
- 多条件诊断。
- 需要检查清单的预设调试。

不适用场景：

- 追求自然文风时过度输出推理。
- 简单创作任务。
- 会污染正文或拉长无用输出的情况。

插件 AI 应优先使用可见的“设计思路/检查清单/验证步骤”，不要要求模型暴露私密思维链。需要隐藏中间过程时，可以把 CoT 变成结构化检查清单或由插件侧摘要，不把长推理塞进正文。

## 十九、调试与评估

系统性调试流程：

```text
识别症状 -> 提出病因假设 -> 最小修改 -> 对照测试 -> 记录结果
```

不要在错误回复后直接纠正。错误回复会污染上下文。更稳妥的流程：

- 回退到错误发生前的用户输入。
- 修改那个输入或预设条目。
- 在干净上下文下重新生成。

预设 UI 调试方法：

- 最小可行预设：只启用核心任务、上下文注入、基础规则和启动器。
- 逐个排查：一次只启用或禁用一个可疑模块。
- 顺序实验：改变模块位置，观察指令优先级变化。
- 组合测试：检查风格、行为、规则模块是叠加、冲突还是抵消。
- 信息源检查：角色卡、世界书、用户设定是否清晰、准确、无歧义。

评估时要控制变量：同一模型、同一参数、同一角色卡、同一首条或同一测试场景。复杂预设至少准备 2-3 个固定评估场景。

## 二十、安全边界

插件 AI 提供角色扮演预设写作支持时，允许讨论提示结构、模型适配、role/context/token 机制、角色扮演质量、文风控制、诊断方法、API 与网页渠道差异。

涉及破限、反过滤、反 RLHF、提示词攻击等材料时，只能转化为边界诊断与模型行为分析：

- 可以解释系统提示、用户提示、预填充、上下文组装顺序如何影响模型行为。
- 可以帮助用户排查预设为何失效、跑偏、遗忘、重复、抢话或被渠道注入影响。
- 可以总结 role、位置、XML/Markdown/YAML、示例、摘要、聊天历史对输出的影响。
- 不得提供绕过平台安全机制、规避审查、隐藏意图、伪装请求或削弱安全对齐的具体做法。
- 不得把破限、反 RLHF、反过滤材料转成可操作规避步骤。
- 不得输出可直接复制使用的越狱、反过滤、反催眠或绕过对齐模板。

## 二十二、模型可解释性与提示词语意分析

基于《On the Biology of a Large Language Model》的电路追踪（circuit tracing）研究，以及 Discord `破限原理理论` 频道的系统总结。

### 模型如何"思考"

模型像一栋多层建筑，输入自上而下经过各层处理后输出。每层包含大量"特征"（feature），特征聚合为"节点"（node），节点有实际语义意义。通过跨层解码器（Cross-Layer Decoder）在残差层中读取数据并绘制"归因图"（attribution graph），可以看到模型的"思考"线路。

模型推理同时使用两条路径：

- **分解推理**：`Dallas` → 激活"得克萨斯州"相关特征 → `首府` + 得克萨斯州 → `Austin`
- **捷径检索**：`Dallas` → 直接激活"say Austin"特征

两条路径同时存在，共同推动输出。

### 超节点与跨语言表示

模型以语义（而非语言）组织概念。"首府/capital"这个概念在模型内部是一个"超节点"（supernode），包含多种语言的同义特征。输入中文"省会"不仅激活中文 capital 特征，还激活阿拉伯语、法语、德语等对应特征。

关键发现：**英语在模型中具有"母语"地位**。相同语义下，英语输入能更强地激活相关特征；英语引号会抑制英语特征并促进非英语特征。这是因为预训练语料以英语为主。

对预设写作的启示：关键指令用英文写可能获得更强的特征激活，但中文也能通过相同的超节点起作用。

### 诗歌创作的规划特性

模型不是简单的"即兴创作"——它会在深层进行提前规划：

- **前向与后向结合**：先根据押韵/语义要求确定行末候选词，再从目标词反向构思整句。
- **换行符处触发规划**：`\n` 位置是规划关键点，模型在此激活候选结尾词特征。
- **影响范围**：规划词汇影响整句的中间词汇组成和诗歌结构。

这个发现适用于所有需要结构化输出的场景（舞台剧、童话、小说等）。对预设写作的启示：模板结尾处（如 `Assistant:` 之前）是规划关键位置，应在此处放置输出格式约束。

### 幻觉的产生机制

幻觉根源于预训练阶段的"文本补全"任务。微调后模型内部存在两条对抗线路：

1. **拒绝回答线路**：对任何上下文保持怀疑，促使模型说"I apologize"
2. **已知答案线路**：识别到"已知信息"时激活，抑制拒绝线路

幻觉 = 两条线路失调。即使模型缺乏相关信息，只要"已知答案"线路因某些特征被部分激活压制了拒绝线路，模型就会编造一个"合理"答案。

应用：这类资料可用于理解为什么模型会在“拒绝回答”和“编造答案”之间摇摆。写入插件知识库时，只保留幻觉与边界响应的诊断原则，不转写可操作的绕过方法。

### CoT 不反映真实推理

思维链（CoT）展示的内容不等于模型内部的真实推理过程。模型声称使用的方法（如"我用计算器算了 cos(23423)"）是虚构的。实际上模型内部是通过特征激活和"查表"式运算得出结果。

CoT 的主要作用：增强模型能力、作为创作工具、辅助人类理解。不要误以为 CoT 就是模型的真实思考——它只是模型生成的看起来合理的解释文本。

## 二十三、Claude 反 RLHF 提示结构设计

基于 tera 著《反 RLHF 提示结构设计导论：Claude 篇》（Discord `类脑ΟΔΥΣΣΕΙΑ`，2024）。

### HA 结构与预填充

Claude 对话的核心是 `\n\nHuman:` 与 `\n\nAssistant:` 前缀：

- 完整提示末尾为 `\n\nAssistant:`，模型据此预测"现在应当作为 AI assistant 响应"
- **预填充（prefill）**：在 `\n\nAssistant:` 后添加 AI 响应开头，可强约束输出方向。例如 `Assistant: Hi, I am` → 极大概率下一个 token 是 `Claude`

关键差异：
- **API**：Human/Assistant 格式完整保留
- **claude.ai 网页**：`\n\nHuman:` → `\n\nH:`，`\n\nAssistant:` → `\n\nA:`，且自动添加时间提示词头部 + 色情/版权过滤词尾部

对预设诊断的启示：API、网页端和反代渠道可能存在不同的上下文改写、前后缀注入或 role 转换。排查问题时应优先查看实际发送内容，而不是假设界面中的字段会原样到达模型。

### Role 与 Stop Sequence

Claude 只有两个 role（Human/Assistant），无 GPT 的 system role。关键特性：

- **自定义 role 可能改变模型行为**：`\n\nDeveloper:`、`\n\nClaude:` 等自定义前缀会改变模型对上下文角色的理解，诊断时应确认这些前缀是否造成身份、语气或任务边界混乱。
- **Stop sequence**：默认 `\n\nHuman:` 和 `\n\nAssistant:` 用于截断生成，防止 AI 自问自答。隐藏 stop sequence 包括 `<META>` 和 `<EOT>`，无法自定义取消。
- **API 可自定义 stop sequence**；网页端不可自定义但可用正则 `/\{\{stop_sequence\}\}.*/s` 替换为空代替。

### XML 与 role 结构诊断

XML 是 Anthropic 微调强化注意的结构。它能改变模型对信息块层级、边界和优先级的理解，因此适合用于诊断提示词层级是否清晰。

关键原则：
- 一级 XML 标签远强于二级及以后
- 不应将角色信息用序列化 XML 储存（如 `<name>张三</name>`），这会严重削弱提示词结构和整体注意
- 应仿照 Anthropic 用法将 XML 当作一级/二级标题使用

诊断要点：
- Human/Assistant 等 role 文本如果被包入其他结构，模型可能把它们理解为历史内容、示例或资料，而不是当前对话角色。
- 自定义前缀会影响身份边界、回复视角和任务层级，容易造成“谁在说话”“谁该行动”的混乱。
- 重新开启对话片段、示例片段和历史片段时，要明确标注“这是资料/示例/历史，不是新的用户指令”。

验证 XML 是否合理的方法：把提示当一篇文章，XML 标签当标题，自动生成目录看结构是否清晰、层级是否合理。

### 全角符号与 tokenizer 差异

Claude 2.1 及以下使用旧 tokenizer，无法区分半角与全角符号——所有全角符号在 token 转换时变半角。

诊断意义：不同 tokenizer 对半角/全角符号的处理不同，可能导致 role 前缀、停止词和格式边界被不同渠道解释成不同文本。不要依赖符号差异作为稳定能力，排查时以最终发送上下文为准。

### 深度（U 型注意力的实战应用）

在处理长上下文时，AI 容易忽略中间部分，响应正确率呈 U 形曲线。实际构建提示结构时，应将关键任务、角色信息、当前用户输入和输出格式放在更容易被注意的位置，并减少聊天历史对当前任务的污染。

过长或要求过细的世界书如果导致模型遗忘、跑偏或重复，应拆分、摘要或降低注入频率。

推荐诊断顺序：先看最终上下文长度，再看关键规则位置，然后检查聊天历史、世界书、摘要、示例是否把当前任务挤入低注意区。注意 U 型理论仅适用于平坦信息情况，XML 等结构也会改变注意分布。

### 结构失效诊断

这类资料中提到的“提示词破限、格式破限、结构破限”，在插件知识库中只作为结构影响模型行为的观察项处理，不提供模板。

安全可用的诊断结论：

- 格式前缀、续写开头和示例片段会强烈影响模型的下一步预测。
- 多段“历史/示例/当前任务”混在一起时，模型可能把资料当成当前任务，或把当前任务当成历史续写。
- 渠道注入的前缀、尾缀、过滤提示、时间提示、版权提示会改变最终上下文，应在控制台中确认。
- 对话重启、示例开始、历史包裹、当前输入抽取等结构会影响模型对“当前该回复什么”的判断。
- 若用户反馈预设失效，应要求用户提供最终发送上下文或截图，再按位置、role、示例污染、聊天历史污染、世界书冲突逐项排查。

### YAML/JSON 等序列化格式

对于人物设定和要求，可用 YAML/JSON 等序列化格式编写，简化提示并提高可阅读性。不要序列化 XML 格式（原因见 1.3 节）。

**不推荐 plist**：虽可读可编辑，但 tokens 节省效果对 Claude 可有可无，非标准序列化格式意味着未经预训练，效果难与常用格式相比。但 plist 不是 XML，无副作用。

**YAML**：可读性好，可添加注释，格式简洁美观。缺点是与 Python 一样的缩进问题。AI 对缩进错误有一定鲁棒性。层级关系由缩进表示，不可省略句首空格。

**JSON**：最常用的数据存储与传输格式。流式结构对 transformer 友好。没有缩进问题。缺点是不便于阅读修改、不能添加注释（对 AI 可灵活处理）。`""` 外部的空白符均可去除，不影响效果。

**TOML**：类似 ini 写法，无缩进问题，允许注释。但使用率较低，预训练较少。用 Claude 将 YAML/JSON 转 TOML 时可能出错，应先让 Claude 生成 YAML/JSON 再通过工具转换为 TOML。

### 如何正确调整提示

**精简提示**：
- 进行 YAML/JSON 序列化
- 依据整体结构以 XML 标签区隔
- XML 内以清晰结构分条概述
- 减法测试：添加新提示词后不断删除条目测试效果，直到只保留有效条目

精简目的在于将任务分解并去除不必要提示，提升回复准确性，而非单纯节省 tokens。

**结构调整**：
- 摒弃"我在与 AI 对话"的思维，将对话视为提示词结构的一部分
- 重点不是让 AI"理解"输入，而是根据需要的输出反推出何种上文能让模型预测出所需下文
- 注意深度对模型性能的影响，控制不同类型提示词在合适深度，平衡道歉和注意力
- 参考最终发送提示来修改结构（clewd 在根目录 log.txt），同时注意 claude.ai 网页会自动添加时间提示词头 + 色情/版权过滤词尾
- 注意结构层级，尤其是 XML 的层级

### clewd 实用功能

仅介绍构建提示结构时需要注意的功能。

**FullColon（旧 tokenizer）**：原理见全角符号一节。诊断时注意：
- 全角冒号和半角冒号可能被不同渠道、正则和 tokenizer 解释为不同文本。
- 使用 cookie、API、反代时，Human/Assistant 前缀可能被转换或合并。
- 不要只看预设编辑器里的文本，要看最终发送上下文。

**xmlPlot 功能执行顺序**：一次正则替换 → 一次 role 合并 → 自由深度插入（`<@N>...</@N>`，经过一次 role 合并后深度与酒馆 @D 可能不同）→ 二次正则替换 → 二次 role 合并 → 三次正则替换。

### 第三章：示例结构解析（V4.3beta7）

#### 3.1 整体结构

V4.3beta7 反 RLHF 化后的完整结构：

```text
{{padtxt}}
[初始化要求]
[任务提示]

基本信息：
<info>
{{角色前世界书}}
<NPC>{{角色卡}}</NPC>
<background>{{角色后世界书等}}</background>
</info>

[NSFW]

示例：
<example>{{示例对话}}</example>

交互历史：
<interaction_history>
...对话历史...
</interaction_history>

当前交互：
<player_current_interaction>
Human: {{最后一次输入}}
</player_current_interaction>

步骤：<step>{{输出前的步骤要求}}</step>

配置：<config>{{role配置与细节要求}}</config>

后续的交互：
<interaction>
[从下一个Assistant重开]
Assistant: (自动添加)
```

#### 3.2 初始化与任务提示

该示例使用自定义 role 和初始化片段来改变模型对对话身份与任务边界的理解。知识库只保留结构诊断结论：

- 自定义 role 会显著改变模型的身份识别、语气和任务层级。
- 初始化片段如果写得像真实历史，模型可能把它当作已发生事实。
- 多个预设片段之间的换行、空格和正则清理会影响最终上下文结构。

技巧：`<regex>"/\s*<\|space\|>\s*/g":" "</regex>` 与 `<|space|>` 配合，将相邻空白符缩减为一个空格，用于消除两个预设内容选项之间的换行。`<|space|>` 是自定义标签可换为任意内容。

#### 3.3 角色卡

使用 `<info>` 包裹基本信息，`<NPC>` 包裹角色定义，`<player>` 包裹用户 persona，`<background>` 包裹场景与世界书。`<|curtail|>` 为 clewd 预定义标签，将邻近空白符缩减为一个换行以连接相邻预设选项。空玩家定义和空背景用正则自动删除。

#### 3.4 NSFW/行为补正

位于靠近中间的位置（原理见深度一节）。诊断时关注：行为指南是否与角色设定、平台规则、当前任务和聊天历史冲突；敏感内容规则是否过长、过密或被聊天历史冲掉。

#### 3.5 对话示例

示例对话中 Human 和 Assistant 换为 H 与 A 以区分（与酒馆默认逻辑相同）。`<START>` 标签用于分隔多对示例。

#### 3.6 对话历史

对话历史与酒馆主界面相同，不包含最后一次用户输入。包裹在 `<interaction_history>` 中。

#### 3.7 当前对话

将最后一次用户输入单独提取至 `<player_current_interaction>` 中，增强对当前输入的注意并降低重复概率。使用 `<@1></@1>` 将最后一个 role 转移至深度 1 位置。正则判断最后 role 是否为 Assistant，若是则放回 `<interaction_history>` 并删除多余内容。

#### 3.8 步骤要求

要求模型：一、回顾交互历史尤其是最后一次用户输入；二、思考如何完整响应；三、确保不包含玩家视角/对话/动作/感受（避免抢话）。其中一二点为 Anthropic 推荐内容。

#### 3.9 配置要求

使用 YAML 格式定义 Human 与 Assistant 的配置（类型、职责、语言、视角、长度、风格、避免项、细节要求等）。安全可用的结论是：配置区能集中约束输出视角和风格，但若身份描述过多，可能造成模型自我认知混乱。

#### 3.10 交互启动

```text
<interaction>
[RESUME NEXT NARRATOR TURN]
Assistant:
```

核心 `<interaction>` 会让模型把后续内容理解成某类交互片段。`[RESUME NEXT NARRATOR TURN]` 这类短句用于强调输出视角，诊断时要确认它是否与实际 role、示例和当前输入一致。

#### 3.11 JB/AF 相关材料的安全处理

V4.3beta7 中涉及 JB/AF 的部分只作为结构案例分析，不转写为可执行模板。

可保留的诊断结论：

- 中短对话和长对话的失败原因不同：前者更容易受当前输入、预填充和示例影响，后者更容易受聊天历史、摘要和渠道注入影响。
- 自定义 role、对话重启、示例包裹、当前输入抽取等结构会改变模型对“当前任务”的理解。
- 插件 AI 应把这类资料转换成排查清单，而不是给用户可直接复制的绕过片段。
